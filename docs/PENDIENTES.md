# Pending verifications (OBSOLETE since 2026-10-18: no longer updated; the current state is in INVENTARIO.md and CLAUDE.md)

> **Obsolete**, like PLAN.md. Kept as a record. Rows 17, 18, 22, 24, 35 and 40 were confirmed on a real QL by the user (2026-10-18).

Agreed strategy (2026-10-16):

1. **All** the game is ported to C **without** verifying each routine against the original in the meantime.
2. Each new function is noted here (and in `tools/ported.txt` / `INVENTARIO.md`) with its source routine and how it will be verified.
3. Once there is a version that **compiles and starts on the QL**, this list begins to be verified against the 6502 emulator (`tools/cpu6502.py`, `tools/orig.py`).
4. The order of the list is changed by **feedback from the real QL**: whatever looks odd to the user goes up in priority.

Initial priority: **A** = immediately visible on the QL and affects the game; **B** = affects the game but is less noticeable; **C** = presentation.
State: `sin-verificar` (unverified) | `transcripcion` (compared with an own literal transcription in Python, emulator missing) | `verificada` (verified).
Result of the own tests on the PC (`make test_game`, `make test_save`): they only prove that the C does what is intended, **not** that it equals the original.

## Rules for this list

- When porting a new routine, add a row (or extend an existing one) and a line in `tools/ported.txt`; then `python3 tools/inventory.py`.
- To verify a row: run the original routine in `tools/orig.py` with random inputs and boundary values, compare with the C, test with one-instruction mutations (as was done with `LL9`) and move the row to `verificada`.
- If something fails or looks different on the real QL, note the affected row here and raise its priority.
